Section 1

Understanding the Attack Class

A software supply chain attack targets the tools, libraries, and infrastructure that build your software — rather than your software itself. The attacker's goal is to inject malicious code into a trusted package so that it executes automatically, on trusted infrastructure, with trusted credentials — without ever touching your production systems directly.

Think of it like a restaurant supplier adulterating ingredients before delivery. The kitchen staff are not negligent — they trust their supplier. But every dish served that evening carries the contaminant. In GCP terms: the malicious package runs inside Cloud Build, on a worker that has IAM permissions. It doesn't need to break any locks — it's already inside.

Why GCP environments are high-value targets Build workers run with service account permissions. Those service accounts frequently have access to Artifact Registry, Secret Manager, GCS buckets, and Workload Identity tokens. A single successful package compromise during npm install or pip install can yield cloud credentials without any credential theft in the traditional sense.

Supply Chain Attack Taxonomy

Dependency confusion
Attacker publishes a public package with the same name as your private internal package. Package managers resolve public over private by default.
Example: your internal @company/utils → attacker publishes @company/utils to npm public registry
Typosquatting
Attacker registers a package name visually similar to a popular one. Relies on developer typos or copy-paste errors.
Example: axios → axois, lodash → 1odash, requests → request-2
Maintainer compromise
Attacker gains control of a legitimate maintainer's account and publishes a malicious version of a genuine, trusted package. Hardest to detect — valid signatures, real history.
Example: TanStack (2026) — OIDC token stolen via GitHub Actions cache poisoning
CI/CD pipeline hijack
Attacker exploits misconfigured GitHub Actions, CircleCI, or Cloud Build to execute code in the context of a trusted pipeline — then uses that context to publish or exfiltrate.
Example: tj-actions/changed-files (2025), Codecov bash uploader (2021)
Malicious postinstall
A package includes a postinstall lifecycle script that executes immediately during npm install or equivalent — before any code review can occur.
Example: Any npm package with scripts.postinstall in package.json
Self-propagating worm
Payload enumerates other packages the victim maintains and republishes them with the same injection — multiplying blast radius automatically.
Example: Mini Shai-Hulud (2025–2026) — 400+ packages compromised from initial foothold
Section 2

How the Attack Flows Through Your GCP Stack

Regardless of attack type, the anatomy is consistent: a compromised package enters your Artifactory proxy, a CI/CD build installs it, lifecycle hooks fire on the build worker, credentials are stolen from memory or environment variables, and either exfiltration occurs immediately or the malicious code is baked into a container image for later execution.

Section 3

Initial Triage — What Exposure Do You Have?

Before activating the full playbook, determine your exposure tier. This dictates which phases are urgent vs. precautionary.

🔴 Tier 1 — Active compromise confirmed

  • Malicious package version in Artifactory cache
  • Cloud Build ran npm/pip install during attack window
  • C2 domain observed in VPC Flow Logs or DNS
  • Unexpected API calls from build service account

🟡 Tier 2 — Possible exposure, investigating

  • Affected package in lockfile but no confirmed build
  • Build ran during window, logs incomplete
  • No C2 traffic observed but image was pushed
  • Artifactory logs unavailable / retention expired

🔵 Tier 3 — Indirect / transitive exposure

  • Affected package is a transitive dependency only
  • Package in lockfile but build uses --ignore-scripts
  • Artifactory confirmed clean cache at time of build

🟢 Tier 4 — Not affected

  • Package family confirmed clean (see vendor advisory)
  • No builds ran during attack window
  • Build pipeline does not use affected ecosystem
  • 72-hour cooldown policy in Artifactory was active
Section 4

Response Phases

How to use this section Work top to bottom. Each phase unblocks the next. Phases 1–2 are time-critical. Phases 3–4 are investigative. Phase 5 is structural hardening — do not skip it. Commands shown target GCP + npm; adapt ecosystem-specific syntax for PyPI, Maven, etc.
Phase 1 Detect & confirm — is the malicious package in your environment? ⏱ First 30 min ▼
1
Identify affected package versions from vendor advisory
Check the package maintainer's advisory, GitHub Security Advisories (GHSA), Snyk, or Socket for the specific version ranges compromised. Not all versions of a package are affected. Document the exact version strings.
For TanStack (example): affected = 42 packages, versions published 2026-05-11 19:20–19:26 UTC.
For any incident: pull the GHSA identifier and pinned version list first.
2
Check Artifactory for cached malicious tarballs
Search for the affected package names and version strings in your Artifactory instance. A cached copy means every subsequent build that calls install will pull the malicious version.
Artifactory UI → Artifacts → Search
  Package name: <affected-package>
  Version: <affected-version-range>
  Repository: your-npm-virtual-repo

# Or via Artifactory REST API:
curl -u user:token \
  "https://<artifactory>/artifactory/api/search/gavc?g=<pkg>&v=<ver>"
3
Search Cloud Build logs for builds that used the affected package
Any build that ran npm install / pip install and resolved the affected package version is potentially compromised. The postinstall hook fires on the build worker.
gcloud logging read \
  'resource.type="build" AND textPayload:"<package-name>"' \
  --project=YOUR_PROJECT \
  --freshness=7d \
  --format=json | jq '.[].jsonPayload'
4
Check for C2 connections in Cloud Audit Logs and VPC Flow Logs
Known C2 indicators from vendor advisories and threat intelligence feeds. For the TanStack incident: filev2.getsession.org, git-tanstack.com. For any incident: block and search for all IOC domains from the advisory.
gcloud logging read \
  '(textPayload:"<c2-domain-1>" OR textPayload:"<c2-domain-2>")' \
  --project=YOUR_PROJECT \
  --freshness=7d

# Also check VPC Flow Logs if enabled:
gcloud logging read \
  'resource.type="gce_subnetwork" AND
   jsonPayload.connection.dest_port="443" AND
   jsonPayload.reporter="SRC"' \
  --freshness=3d
5
List container images built during the exposure window
Any image pushed after an infected build is potentially compromised — the malicious code is baked into a layer and will execute when the container starts.
gcloud artifacts docker images list \
  REGION-docker.pkg.dev/PROJECT/REPO \
  --filter="createTime><WINDOW-START>"
Phase 2 Contain — stop further spread immediately ⏱ First 1–2 hours ▼
Do this first — before credential rotation Until the malicious package is blocked in Artifactory, every new build is a potential reinfection — even after you rotate credentials. Block the tarball before anything else.
1
Block the malicious package versions in Artifactory
Add affected versions to your blocked artifact list. This prevents any future build from pulling them, regardless of what version is in their lockfile.
Artifactory → Security → Blocked Artifacts → Add Rule
  Repository: your-npm-virtual-repo
  Package: <affected-package>
  Version: <exact affected versions>

# Via JFrog CLI:
jfrog rt dl --dry-run "<repo>/<pkg>/-/<pkg>-<ver>.tgz"
jfrog rt delete "<repo>/<pkg>/-/<pkg>-<ver>.tgz"
2
Block C2 domains at Cloud DNS and VPC firewall egress
Even if compromise already occurred, blocking C2 cuts ongoing exfiltration and command channels. Use both DNS response policy (prevents resolution) and firewall rules (blocks established connections by IP range if domain resolves via DoH).
# VPC egress block for build worker subnet:
gcloud compute firewall-rules create block-supply-chain-c2 \
  --direction=EGRESS --priority=100 \
  --action=DENY --rules=tcp:443 \
  --target-tags=build-worker \
  --destination-ranges=<c2-ip-ranges>

# Cloud DNS response policy (blocks resolution):
gcloud dns response-policies rules create block-c2-domain \
  --response-policy=my-response-policy \
  --dns-name="<c2-domain>." \
  --local-data=name="<c2-domain>.",type=A,rrdata=0.0.0.0
3
Pause CI/CD pipelines that use the affected ecosystem
Disable Cloud Build triggers for any pipeline that runs npm install, pip install, or equivalent until the dependency tree is verified clean. This prevents new infections while investigation is underway.
# List all triggers:
gcloud builds triggers list --project=YOUR_PROJECT

# Disable specific trigger:
gcloud builds triggers run TRIGGER_ID --no-run

# Or via Cloud Console: Cloud Build → Triggers → disable
4
Quarantine suspect container images in Artifact Registry
Tag images built during the exposure window as quarantined. Update GKE deployment manifests to pin to the last known-good image digest. Do not delete yet — preserve for forensics.
gcloud artifacts docker images add-tag \
  REGION-docker.pkg.dev/PROJECT/REPO/IMAGE:TAG \
  REGION-docker.pkg.dev/PROJECT/REPO/IMAGE:QUARANTINED-<date>

# Pin GKE deployments to last clean digest:
kubectl set image deployment/<name> \
  <container>=<image>@sha256:<last-clean-digest> \
  -n <namespace>
Phase 3 Credential rotation — assume everything reachable was stolen ⏱ Within 4 hours ▼
Rotate broadly — don't try to scope narrowly Supply chain payloads are designed to harvest everything from the build worker environment. Trying to determine exactly what was stolen before rotating credentials wastes time and leaves you exposed. Rotate all credentials reachable from the build worker, then investigate.
1
Rotate Cloud Build service account credentials
# List keys for build SA:
gcloud iam service-accounts keys list \
  --iam-account=BUILD-SA@PROJECT.iam.gserviceaccount.com

# Delete all user-managed keys:
gcloud iam service-accounts keys delete KEY_ID \
  --iam-account=BUILD-SA@PROJECT.iam.gserviceaccount.com

# Prefer Workload Identity Federation — no static keys to steal
2
Rotate all secrets reachable from the build worker
The payload specifically targets: GitHub tokens, SSH keys, Kubernetes SA tokens, .npmrc / .pypirc credentials, AWS access keys, and GCP service account keys stored as environment variables.
3
Rotate Secret Manager secrets accessible by the build SA
# Find secrets with IAM binding for build SA:
gcloud secrets list --project=PROJECT

# For each sensitive secret — add new version, disable old:
gcloud secrets versions add SECRET_NAME \
  --data-file=new-value.txt

gcloud secrets versions disable PREV_VERSION \
  --secret=SECRET_NAME
4
Audit Cloud KMS — rotate keys reachable from build workers
If the build SA had access to KMS key rings, treat all data encrypted with those keys as potentially accessible to the attacker. Rotate keys and re-encrypt sensitive data.
gcloud kms keys list \
  --location=global \
  --keyring=YOUR_KEYRING

# Check IAM bindings for each key reachable from build SA
gcloud kms keys get-iam-policy KEY_NAME \
  --location=global --keyring=KEYRING
Phase 4 Forensics — establish scope, timeline, and evidence ⏱ Within 24 hours ▼
1
Preserve all logs immediately — before retention windows expire
gcloud storage buckets update gs://YOUR-IR-BUCKET \
  --retention-period=7776000 # 90 days

# Export Cloud Audit Logs to GCS for analysis:
gcloud logging sinks create ir-evidence-sink \
  storage.googleapis.com/IR-BUCKET \
  --log-filter='timestamp>="<WINDOW-START>"'
2
Audit all data access by the build service account post-exposure
gcloud logging read \
  'protoPayload.authenticationInfo.principalEmail="build-sa@PROJECT.iam.gserviceaccount.com"
   AND timestamp>="<EXPOSURE-WINDOW-START>"' \
  --limit=1000 --format=json | \
  jq '.[].protoPayload | {method:.methodName, resource:.resourceName}'
Look for: unusual GCS object reads, Secret Manager access, BigQuery job creation, new IAM bindings, API calls at unusual hours.
3
Inspect container image layers for the injected payload
docker pull SUSPECT_IMAGE

# Search for payload file by name or size:
docker run --entrypoint sh SUSPECT_IMAGE -c \
  "find /app/node_modules -name '<payload-filename>' -size +1M 2>/dev/null"

# Inspect each layer for unexpected additions:
docker history --no-trunc SUSPECT_IMAGE
docker save SUSPECT_IMAGE | tar -xv # extract all layers
4
Check GKE audit logs for anomalous pod behavior
gcloud logging read \
  'resource.type="k8s_cluster"
   AND protoPayload.methodName=("io.k8s.core.v1.pods.exec"
   OR "io.k8s.core.v1.pods.portforward"
   OR "io.k8s.core.v1.secrets.get")
   AND timestamp>="<WINDOW-START>"'
Note: GKE metadata server queries may not appear in standard audit logs. Enable Workload Identity audit logging separately and check node-level syslog if GKE node logging is enabled.
5
Check whether your own published packages were re-infected
Self-propagating worms enumerate packages the victim maintains via the registry API and republish them with the injection. Check your published packages for unexpected version bumps during the attack window.
# Check npm for unexpected versions:
npm view @your-org/your-package versions --json

# Check Artifact Registry for unexpected image tags:
gcloud artifacts docker images list \
  REGION-docker.pkg.dev/PROJECT/REPO \
  --filter="createTime><WINDOW-START>" \
  --format="table(package,tags,createTime)"
Phase 5 Structural hardening — close the gaps that made this possible ⏱ Within 1–2 weeks ▼
1
Enable a package version cooldown policy in Artifactory ⭐ Highest impact
Configure Artifactory to hold newly published package versions for 72 hours before serving them to CI/CD. This is the single control that would have prevented the TanStack attack entirely — the malicious versions were deprecated within 20 minutes. Cooldown is available via JFrog Artifactory's "Xray Watch" or a custom proxy rule.
2
Disable lifecycle scripts in CI/CD installs
Lifecycle hooks (postinstall, preinstall) are the primary execution vector. Disabling them removes the attack surface entirely for most payloads.
# npm — in cloudbuild.yaml:
- name: 'node:20'
  entrypoint: npm
  args: ['install', '--ignore-scripts']

# pip — use --no-build-isolation or audit wheels separately
# Maven — disable exec plugin in CI profile
3
Apply least privilege to build service accounts
Build workers almost never need access to production GCS, BigQuery, Secret Manager, or KMS. Use separate service accounts per environment (dev/staging/prod) and scope each tightly.
# Minimum viable build SA roles:
roles/logging.logWriter
roles/artifactregistry.writer      # push images only
roles/storage.objectCreator        # write build artifacts only

# Remove any broad roles:
gcloud projects get-iam-policy PROJECT \
  --flatten="bindings[].members" \
  --filter="bindings.members:build-sa@" \
  --format="table(bindings.role)"
4
Enable JFrog Xray behavioral scanning in Artifactory
Xray scans package contents for malicious lifecycle scripts, known CVEs, and license violations before serving them to consumers. Enable it on all npm and PyPI virtual repositories. This is Artifactory's biggest structural gap in this attack class.
5
Use Workload Identity Federation — eliminate long-lived SA keys
Static service account keys in environment variables are the most valuable credential for attackers. Workload Identity Federation issues short-lived tokens tied to the specific workflow — stolen tokens expire in minutes, not years.
# Bind Cloud Build to WIF instead of SA key:
gcloud iam workload-identity-pools create "cicd-pool" \
  --project=PROJECT \
  --location="global"

# Scope token to specific repo + branch only:
gcloud iam service-accounts add-iam-policy-binding \
  BUILD-SA@PROJECT.iam.gserviceaccount.com \
  --role="roles/iam.workloadIdentityUser" \
  --member="principalSet://iam.googleapis.com/projects/.../attribute.repository/org/repo"
6
Enable GCP Security Command Center + alert on build anomalies
Configure alerting on: unexpected service account API calls outside business hours, new IAM role bindings, outbound connections from build worker subnets to uncategorized domains, and unexpected image pushes to Artifact Registry.
